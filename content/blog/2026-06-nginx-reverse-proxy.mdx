> 结论先说：生产环境把 TLS、反向代理、限流和静态缓存交给 Nginx，后端只听内网端口——比每个服务各自挂证书稳得多。

## 为什么需要 Nginx

即使你的应用已经按 [[docker-deploy-guide]] 跑在容器里，直接暴露端口到公网也不是好主意。Nginx 作为反向代理层，能帮你做：

- **HTTPS 终端**——处理 SSL/TLS 握手，后端服务用 HTTP 就行
- **负载均衡**——多个实例分摊流量
- **静态资源缓存**——图片/CSS/JS 直接由 Nginx 返回，不经过后端
- **请求限流**——防止恶意请求打垮后端
- **访问日志**——统一的流量记录

## 安装

```bash
# Ubuntu/Debian
sudo apt install -y nginx

# 验证
nginx -v
sudo systemctl status nginx
```

配置文件目录：`/etc/nginx/`，主配置文件：`/etc/nginx/nginx.conf`

## 基础站点配置

在 `/etc/nginx/sites-available/` 下创建配置文件，然后在 `sites-enabled/` 里软链接：

```bash
sudo nano /etc/nginx/sites-available/myapp
sudo ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/
```

下面的示例适用于**静态导出的 SPA**。Next.js SSR 等需要 Node 运行时的应用不能把页面请求回退到 `dist/index.html`；应把 `location /` 改为反向代理到应用，例如 `proxy_pass http://127.0.0.1:3000;`，并配置与 API 相同的转发头。静态目录和哈希资源的匹配规则也要按实际构建产物调整。

**先签发证书，再启用 HTTPS 配置。** 首次部署时只启用下面的 HTTP 引导配置，创建挑战目录并确认域名 A/AAAA 记录指向这台服务器、80 端口可达；用 ACME 客户端完成 HTTP-01 验证和证书签发后，再替换为后面的 HTTPS 配置。不要在证书文件不存在时引用它们，否则 `nginx -t` 会失败。

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name example.com;

    location /.well-known/acme-challenge/ {
        root /var/www/letsencrypt;
    }

    location / {
        return 503;
    }
}
```

以已安装的 Certbot 为例，先创建目录、验证配置并重载，再签发：

```bash
sudo mkdir -p /var/www/letsencrypt
sudo nginx -t
sudo systemctl reload nginx
sudo certbot certonly --webroot -w /var/www/letsencrypt -d example.com
```

静态 SPA 的 HTTPS 配置示例：

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name example.com;

    # 保留 HTTP-01 挑战入口，供证书续期使用
    location /.well-known/acme-challenge/ {
        root /var/www/letsencrypt;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name example.com;

    # SSL 证书（Let's Encrypt）
    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # 安全头
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    # 静态资源——直接由 Nginx 处理，不转发到后端
    # 示例匹配 app.0123456789abcdef.js；按实际构建的哈希命名规则调整
    location ~* "\.[0-9a-f]{8,}\.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$" {
        root /var/www/myapp/dist;
        expires 1y;
        add_header Cache-Control "public, immutable";
        # 子 location 定义 add_header 后，显式重复需要的安全头
        add_header X-Frame-Options "SAMEORIGIN" always;
        add_header X-Content-Type-Options "nosniff" always;
        add_header Referrer-Policy "strict-origin-when-cross-origin" always;
        try_files $uri =404;
        access_log off;
    }

    # 非哈希静态文件使用短缓存，不使用 immutable
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$ {
        root /var/www/myapp/dist;
        expires 5m;
        try_files $uri =404;
    }

    # API 请求——转发到后端服务
    location ^~ /api/ {
        proxy_pass http://127.0.0.1:3000/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时设置（WebSocket 需要更长超时）
        proxy_connect_timeout 60s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;
    }

    # 前端路由——SPA fallback
    location / {
        root /var/www/myapp/dist;
        try_files $uri $uri/ /index.html;
    }
}
```

`immutable` 只适用于内容变更后 URL 也变化的资源；`logo.svg` 等固定文件名不应缓存一年。传统 `add_header` 规则只在当前层没有任何 `add_header` 时继承上层，因此哈希资源的 location 显式保留了安全头。以上示例不依赖较新版本的继承控制指令。

证书续期还需要 ACME 客户端的定时任务及成功续期后的 Nginx reload hook；上线前应检查续期任务并执行 `sudo certbot renew --dry-run`。本文未在实际服务器执行这些部署命令。

验证配置并重载：

```bash
sudo nginx -t          # 先验证语法
sudo systemctl reload nginx  # 重载（不中断现有连接）
```

## 反向代理到 Docker

如果你的应用跑在 Docker 容器里，有两种方式连接：

**方式一：端口映射 + localhost**

```bash
sudo docker run -d -p 127.0.0.1:3000:3000 myapp
```

这种方式适用于 **Nginx 运行在宿主机**：容器端口只映射到宿主机 loopback，Nginx 使用 `proxy_pass http://127.0.0.1:3000;`。应用在容器内应监听 `0.0.0.0:3000`。

**方式二：Nginx 与应用都运行在 Docker 网络中**

```bash
# 创建 bridge 网络
sudo docker network create webnet

# 启动应用容器，加入网络
sudo docker run -d --name myapp --network webnet myapp

# Nginx 容器也用同一个网络
sudo docker run -d --name nginx-proxy --network webnet \
  -p 80:80 -p 443:443 \
  -v /srv/nginx/conf.d:/etc/nginx/conf.d:ro \
  -v /etc/letsencrypt:/etc/letsencrypt:ro \
  -v /var/www/letsencrypt:/var/www/letsencrypt:ro \
  -v /var/www/myapp/dist:/var/www/myapp/dist:ro \
  nginx:alpine
```

启动前准备 `/srv/nginx/conf.d/myapp.conf` 和对应的证书、挑战目录及静态构建产物。挂载写出宿主路径与容器路径并设为只读；挂载整个 `/etc/letsencrypt` 才能保留 `live` 指向 `archive` 的证书软链接。首次签发仍先使用 HTTP 引导配置，签发完成后验证并重载容器内 Nginx。应用无需发布宿主机端口，容器内监听 `0.0.0.0:3000`。

Nginx 里直接用容器名（容器内的 `127.0.0.1` 指向 Nginx 自己）：

```nginx
location /api/ {
    proxy_pass http://myapp:3000/api/;
}
```

## 负载均衡

多个实例分摊流量，提高可用性和吞吐量：

```nginx
upstream backend {
    # 加权轮询
    server 127.0.0.1:3000 weight=3;
    server 127.0.0.1:3001 weight=1;
    server 127.0.0.1:3002;

    # keepalive 连接复用
    keepalive 32;
}

server {
    listen 80;
    server_name example.com;

    location /api/ {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

负载均衡策略：

| 策略     | 配置          | 适用场景           |
| -------- | ------------- | ------------------ |
| 轮询     | 默认          | 各实例性能相近     |
| 加权轮询 | `weight=N`    | 实例性能不同       |
| IP 哈希  | `ip_hash;`    | 需要会话保持       |
| 最少连接 | `least_conn;` | 请求处理时长差异大 |

## 请求限流

防止爬虫或攻击打垮后端：

```nginx
# 在 http 块中定义限流区域
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

server {
    listen 80;
    server_name example.com;

    location /api/ {
        limit_req zone=api burst=20 nodelay;
        proxy_pass http://backend;
    }
}
```

参数解释：

- `rate=10r/s`：按漏桶机制限制每个键的平均处理速率，不是按自然秒统计的硬上限
- `burst=20`：允许最多 20 个超出当前速率的请求占用突发额度；再超出时拒绝请求，默认状态码为 503，可用 `limit_req_status 429;` 调整
- `nodelay`：额度内的突发请求立即放行，但已占用的额度仍按配置速率释放；去掉它才会延迟处理这些请求

此处按客户端 IP 分组。若前面还有 CDN 或代理，应先配置受信任的真实 IP 来源；不能直接信任任意请求带来的转发头，否则限流可能失效。

## 访问日志优化

默认 Nginx 会记录每次请求的完整日志，时间长了磁盘吃紧：

```nginx
# log_format 放在 http 块中，末尾记录整个请求处理时间（秒）
log_format slim '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                '"$http_referer" "$http_user_agent" $request_time';

access_log /var/log/nginx/access.log slim buffer=32k flush=5s;

# 对静态资源关闭日志
location ~* \.(css|js|png|jpg)$ {
    access_log off;
}
```

## 常用诊断命令

```bash
# 测试配置语法
sudo nginx -t

# 重载配置
sudo systemctl reload nginx

# 查看错误日志
sudo tail -f /var/log/nginx/error.log

# 查看访问日志中的慢请求
sudo awk '$7 ~ /^\/api\// && $NF ~ /^[0-9]+([.][0-9]+)?$/ {print $NF, $0}' \
  /var/log/nginx/access.log | sort -nr | head -20

# 查看 Nginx 状态（如果开启了 stub_status）
curl http://127.0.0.1/nginx_status
```

上述慢请求命令只适用于本文定义的 `slim` 格式：请求路径是第 7 列，最后一列是 `$request_time`。切换格式前的旧日志不适用；它衡量完整请求耗时，排查后端时可进一步记录 `$upstream_response_time`。

## 总结

Nginx 是部署流程里最值得花时间配置好的环节。一个合理的 Nginx 层能让后端服务更简单——只管处理业务逻辑，安全、缓存、限流全交给 Nginx。
