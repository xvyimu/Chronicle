> 结论先说：View Transitions 是**渐进增强**，不是品牌大片。只在列表→详情这类「空间连续」导航上点缀；必须尊重 `prefers-reduced-motion`，且绝不能拖坏 INP。

> **时效注（2026-10）**：下文提到数字花园力导向图作为 `usePrefersReducedMotion` 的历史用例；该功能已在 2026-10-07 重构中移除，钩子本身仍可复用于现有交互。删除决策见 `docs/adr/0007-workspace-rebuild-baseline.md`。

服务端组件与导航模型见 [[nextjs-app-router|Next.js App Router 实战]]；动效与 CWV 的关系见 [[web-performance-optimization|Web 性能优化实战]]。

## 浏览器能力与 Next 封装

[View Transitions API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API) 让浏览器在 DOM 更新前后截两帧，做交叉淡化或共享元素动画。当前 Next.js 16 App Router 可直接使用 React 的 View Transition 能力；本站使用的 Next.js 16.3.8 不再需要 `experimental.viewTransition` 配置。

```tsx
import Link from 'next/link';

<Link href={`/blog/${post.slug}`} transitionTypes={['blog-detail']}>
  {post.title}
</Link>;
```

要点：

1. **`transitionTypes` 是 `string[]`**，不是字符串。写 `transitionTypes="blog-detail"` 会在类型检查阶段失败。
2. 类型名是**约定字符串**，用于 CSS 里按类型定制动画；全站先从一个类型开始，避免命名爆炸。
3. 不支持的浏览器会静默退化为普通导航——这是正确默认，不要 polyfill 强行补动画。

## 什么时候该用

| 适合                       | 不适合                      |
| -------------------------- | --------------------------- |
| 博客卡片 → 文章详情        | 搜索结果每一击              |
| 同布局下的分页切换（谨慎） | 表单提交后的重定向          |
| 作品集网格 → 详情          | 主题切换（用 CSS 变量即可） |

作为起点，可先在一处列表到详情导航中验证体验，再根据真实浏览器覆盖与用户反馈决定是否扩展；这不是通用的数量上限。全站每个链都加 transition 会让用户觉得站点「粘」。

## CSS 侧最小集

```css
/* 仅在用户未要求减少动效时启用 */
@media (prefers-reduced-motion: no-preference) {
  ::view-transition-old(root),
  ::view-transition-new(root) {
    animation-duration: 180ms;
    animation-timing-function: ease-out;
  }
}

@media (prefers-reduced-motion: reduce) {
  ::view-transition-group(*),
  ::view-transition-old(*),
  ::view-transition-new(*) {
    animation: none !important;
  }
}
```

View Transitions 的减少动效应优先交给 **CSS 媒体查询**，避免 JS 与浏览器默认策略打架。示例不假定本站存在某个特定的画布或导航图功能。

## 与 RSC / 流式渲染的边界

View Transition 发生在**客户端导航**完成、DOM 提交的窗口。它不改变：

- 服务端组件数据获取
- Suspense 流式块的到达顺序
- CSP nonce 每请求生成

因此：**不要**为了「动画更顺」把本该服务端的数据拉到客户端。动画只装饰已决定的 HTML 差分。

## 性能预算

1. **先从短时长开始试验**。例如可用 180ms 作为初始值，再通过设备测试和用户反馈调整；200ms 不是普适硬阈值。
2. **避免大面积 filter / blur**。低端机 GPU 会掉帧，直接伤 INP。
3. **共享元素要克制**。同一过渡快照中重复的 `view-transition-name` 可能造成非预期的共享元素匹配；名称应明确且只分配给预期的一对元素。
4. **测量**：Chrome Performance 面板检查过渡期间的长任务与掉帧；再用真实交互测量评估是否损害体验，对照 [[web-performance-optimization|性能文]] 的指标解释。

## 与 React Compiler 的协作

Compiler（见 [[react-compiler-in-practice|React Compiler 生产笔记]]）降低导航后无关子树重渲染，让 transition 截到的「新帧」更干净。二者正交：一个管渲染成本，一个管帧间插值。

## 故障排查

| 现象         | 排查                                                                  |
| ------------ | --------------------------------------------------------------------- |
| 完全无动画   | 系统是否开了减少动效；浏览器是否支持；是否确实发生了客户端导航        |
| 整页白闪     | 是否有冲突的 `view-transition-name`；旧页是否在 transition 中卸载过快 |
| 类型报错     | `transitionTypes` 是否写成了字符串而非数组                            |
| 仅生产无动画 | 是否被旧版浏览器或内嵌 WebView 降级（属预期）                         |
