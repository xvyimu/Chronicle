> 结论先说：Biome 的**速度优势是真实的**（本仓实测 `check` 0.41s vs Prettier 2.22s），**格式化兼容性也过关**（对同一份源码逐字一致）。但它的价值不只在「快」——迁移的真难点是**规则集对齐**：Biome 默认 `recommended` 对本仓报出 35 个 error，而定制过的 ESLint 报 0 个。这篇文章记录一次真实仓库上的评估过程与实测数字，不吹「无痛迁移」。

本仓当前工具链是 ESLint 9（flat config）+ Prettier 3 + husky + lint-staged。工具链的取舍原则见 [[cicd-pipeline-design|CI/CD 流水线设计]]，本文只谈 Biome 这一条候选路径。

## 实测环境

评估在仓库的**隔离目录**里做，未改动仓库本身（`git status` 保持干净）：

| 项         | 值                                       |
| ---------- | ---------------------------------------- |
| Biome      | `@biomejs/biome` **2.5.15**              |
| 对比工具   | ESLint 9 + Prettier 3.9.3（本仓现役）    |
| 被测代码   | 本仓 `src/`，**232 个文件**              |
| 机器       | Node 24.16 / Windows 11                  |

## 格式化：逐字一致

第一步是确认 Biome 能否复刻 Prettier 的输出。本仓 `.prettierrc` 有 8 个选项，`biome migrate prettier` 能自动转换：

| Prettier            | Biome                                        |
| ------------------- | -------------------------------------------- |
| `printWidth: 90`    | `formatter.lineWidth: 90`                    |
| `singleQuote: true` | `javascript.formatter.quoteStyle: "single"`  |
| `semi: true`        | `javascript.formatter.semicolons: "always"`  |
| `trailingComma`     | `javascript.formatter.trailingCommas`        |
| `tabWidth: 2`       | `formatter.indentWidth: 2`                   |
| `arrowParens`       | `javascript.formatter.arrowParentheses`      |
| `endOfLine: "lf"`   | `formatter.lineEnding: "lf"`                 |
| `bracketSpacing`    | `formatter.bracketSpacing`                   |

迁移后对真实源文件做对比：Biome 格式化 `src/lib/utils.ts` 的结果，与 Prettier 用 `.prettierrc` 的输出**逐字相同**（`diff` 无输出）。对本仓这种已被 Prettier 长期格式化的代码库，切换格式化器不会产生一次性的大 diff。

## 速度：check 快 5.4 倍

同一批文件、预热后各跑两遍取稳定值：

| 命令                       | 耗时       | 相对       |
| -------------------------- | ---------- | ---------- |
| Biome `check src/`         | **0.41s**  | 1×         |
| Prettier `check src/`      | **2.22s**  | 5.4× 慢    |
| ESLint `src/`              | **7.75s**  | 18.9× 慢   |

Biome 单次 `check` 同时做 lint + format，而 ESLint 单独跑就 7.75s。这就是它宣称的核心卖点，实测成立。

一个方法学提醒：第一次用 `npx --yes @biomejs/biome` 测出 4.9s，比 Prettier 还慢——那是 **npx 的解析/下载开销**，不是 Biome 本身。换成 `node_modules/.bin/biome` 本地可执行后才拿到 0.41s。**测工具速度必须排除启动器开销**，否则结论会反过来。

## 真正的难点：规则集不对齐

这是评估中最值得记录的部分。Biome 在**仓库没有 `biome.json`** 时用默认 `recommended` preset，对同一份 `src/` 报出：

```
Found 35 errors.
Found 59 warnings.
Found 9 infos.
```

而本仓的 ESLint 报 **0 issue**。按规则归类：

| Biome 规则                        | 命中数 | 本仓 ESLint 是否报 |
| --------------------------------- | ------ | ------------------ |
| `style/noNonNullAssertion`        | 33     | 否（未启用）       |
| `style/useImportType`             | 11     | 否                 |
| `a11y/noSvgWithoutTitle`          | 11     | 否                 |
| `complexity/noImportantStyles`    | 9      | 否                 |
| `style/useTemplate`               | 6      | 否                 |
| `suspicious/noArrayIndexKey`      | 5      | 否                 |
| `next/server` · `next/link` · `next/image` | 7 | 部分重叠 |

这些**不是「Biome 更严所以更差」**——它们多数是合理的规则（`noNonNullAssertion` 就是禁 `!` 断言）。问题是：本仓的 ESLint 配置是**定制过的**，比如显式关掉了 `react-hooks/set-state-in-effect`（理由写在配置注释里：`localStorage` 初始化、DOM 测量等合法场景），并补了 `eslint-config-next` 未启用的四条 jsx-a11y 规则。

**迁移的真实工作量在「把这 35 + 59 条逐条判定」**：哪些该修代码、哪些该在 `biome.json` 里关掉、哪些是真问题。这跟「换个更快命令」是两回事。

一个正面发现：Biome **内置 Next.js 规则**（`next/server`、`next/link`、`next/image` 都有命中），不是只能替代 Prettier。

## 决策框架

| 你的情况                                     | 建议                                          |
| -------------------------------------------- | --------------------------------------------- |
| 新项目，还没定 lint 栈                       | Biome 值得首选——一份配置管 lint + format     |
| 代码库小、规则集接近 `recommended`           | 迁移成本低，速度收益直接兑现                  |
| **代码库大、规则集深度定制**（如本仓）       | 先做本文这种隔离评估，把规则差异列全再决定    |
| 依赖 ESLint 插件生态（Next 特有规则之外）    | 确认 Biome 有对应规则或用 `// biome-ignore` 兜 |

本仓的结论：**暂不迁移**。速度收益真实，但现有 ESLint 配置承载了具体的、有注释记录的决策（哪些规则为什么关），迁移要先消化 94 条规则差异，收益（对 232 文件的小仓，省约 7s）不足以覆盖风险。

## 如果真要迁，顺序

1. **隔离目录先跑** `biome init` + `biome migrate eslint --include-inspired` + `biome migrate prettier`。
2. **`biome lint` 全量跑一遍**，把报出的规则**逐条归类**（改代码 / 关规则 / 真 bug）。
3. **格式化对比**：`biome format` 产物与 Prettier 做 `diff`，确认无意外重排。
4. **CI 双跑一轮**：新旧工具并行，观察是否有 Prettier 过而 Biome 不过的边界。
5. 稳定后再移除 ESLint + Prettier 依赖与 husky 钩子里的引用。

## 检查清单

- [ ] 用本地可执行测速，不用 `npx --yes`（排除启动器开销）
- [ ] `biome migrate prettier` 后对真实源文件做 diff，确认逐字一致
- [ ] `biome lint` 的报错**逐条**归类，不整体接受也不整体关闭
- [ ] 确认原 ESLint 配置里的「为什么关这条」注释，在 Biome 侧有等价处理
- [ ] 确认 Biome 覆盖你依赖的框架规则（Next / React 等）
- [ ] 迁移前保留可回滚点（本仓做法：隔离目录，不碰仓库）
